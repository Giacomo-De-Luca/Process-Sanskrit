# csl-inflect update assessment

Assessed on 2026-09-15 against Process-Sanskrit `e97d830` and the local
`references/csl-inflect` checkout at
`e9c11f563be690c872d4371843e7b11c64e3e58b`.

**Follow-up, 2026-09-16:** the first/third-person reversal identified below is
now fixed, with regression coverage and a morphology-cache version bump. See
[the implementation notes](analysis-audit.md#verb-person-correction-2026-09-16).
The assessment below records the pre-fix findings; alternative-form matching
and the single-result verb policy remain open.

## Recommendation

The recent csl-inflect changes do **not justify replacing the morphology
database on their own**. Its nominal, verb, and SQLite source trees are
identical to those available last year. The useful new backend change repairs
Huet extraction; it does not include new inflection tables.

There is immediate value in correcting how Process-Sanskrit reads its existing
tables: first/third-person labels are reversed, and slash-separated alternatives
lose some or all grammatical tags. These are existing integration defects,
independent of the recent upstream updates. This assessment changes no runtime
code or database data.

### Limits of an upstream rebuild

Root `redo.sh` runs `nominals → verbs → sqlite`; it does not refresh Huet XML.
The verb pipeline runs `inputs → models → bases → tables`; it does not run the
manual reconciliation stages either. Updating XML and fixing extraction thus
does not automatically replace the manually incorporated verb tables.

The mapping dictionary has **34 spelling overrides**. The manual's repeated
claim of a 678-entry mapping confuses it with the 678-line annotated text file.
It also still describes the now-fixed `ben`/`prf` bug as open. Use the manual as
a guide, with source verification, rather than as an authoritative data manifest.

Our installed database already contains 592 benedictive paradigms and 807
perfect paradigms. The extraction fix must not be interpreted as proof that
these tenses are currently absent here.

## How Process-Sanskrit actually consumes csl-inflect

The package queries four tables in its own combined, IAST-transliterated
`SQliteDB.sqlite`; it does not import the reference checkout at runtime.

| Table | Purpose | Installed rows |
| --- | --- | ---: |
| `lgtab1` | Nominal paradigms | 289,361 |
| `lgtab2` | Inflected nominal form → model and stem | 4,334,350 |
| `vlgtab1` | Verb paradigms | 11,723 |
| `vlgtab2` | Inflected verb form → model and base | 107,079 |

`functions/SQLiteFind.py` joins the inverse indexes to full paradigms, uses
`refs` to recover dictionary headwords, and passes cells to `utils/paradigm.py`
for tags. `utils/loadResources.py` loads the packaged `type_map.tsv` for model
descriptions. Every model code in the installed morphology tables has a mapping.
Upstream's fifth table, `lgmodel` (descriptions and Kale references), is absent
from this installed database; adopting it would be an optional new feature.

`setup/updateDB.py` downloads our own release asset, pinned to `v1.0.2`, when
the database is missing. For an existing database it repairs the derived
dictionary index; it does not rebuild csl-inflect tables or replace them from
upstream. Updating the reference checkout, rerunning `update-ps-database`, or
changing the release tag alone does not refresh an existing installation's
morphology. See [database setup](database-setup.md).

The main tracked tree contains no full csl-inflect-to-combined-database builder
or recorded csl-inflect source revision for the released asset. A future refresh
needs explicit provenance and the SLP1-to-IAST conversion step, while preserving
model identifiers, reference structure, table positions, and lookup indexes.

## Confirmed opportunities in our current usage

### 1. Correct verb-person labels — highest priority

Upstream and our stored tables use **third, second, first** person, with three
numbers per person. `utils/paradigm.py:28` uses `First, Second, Third`.

Direct probes against the installed database:

| Form | Current lookup tag | Required tag |
| --- | --- | --- |
| `bhavati` | First, Sg | Third, Sg |
| `bhavāmi` | Third, Sg | First, Sg |
| `gacchati` | First, Sg | Third, Sg |
| `gacchāmi` | Third, Sg | First, Sg |
| `gacchathaḥ` | Second, Du | Second, Du |

The existing optimization test checks the unaffected second-person row, so it
passes despite the reversal. Source confirmation is in
`references/csl-inflect/huetdata/readme.md` and the `3p/2p/1p` ordering of
`verbs/pysanskritv2/manual/tables_ben.txt`.

### 2. Recognize alternatives within a paradigm cell — highest priority

Upstream index builders split each colon-separated cell on `/`. Our
`tags_for()` compares the complete cell to the queried word. A valid form can
therefore have an inverse-index hit but no matching tag, or an incomplete set.

- `āpat` and `āpsīt`: both resolve to `āp`, model `aor-a`, but return `None`
  for tags because the stored cell is `āpat/āpsīt`.
- `asakhāyā`: resolves to `asakhi`, model `m_irr`, but loses its Nom. Du. tag.
- `asakhāyau`: returns Acc. Du. and Voc. Du., but misses Nom. Du. because that
  cell is `asakhāyau/asakhāyā`.

824 verb paradigms and 18,741 nominal paradigms contain `/`. These are counts
of tables exposed to this parsing issue, not counts of failed user queries.
Matching alternatives within each cell should preserve the existing 9/24-cell
layout and raw returned table strings.

### 3. Review the one-result verb policy — separate behavior decision

`SQLiteFind.py` deliberately takes the last matching `vlgtab2` row and only
one joined paradigm. Of 98,441 distinct verb keys, 7,761 have multiple index
rows; 5,174 have more than one distinct model. Some rows describe equivalent
base/root variants, so these are not counts of distinct valid interpretations.

For example, `abhavata` has both `ipf-1a` and `ipf-1m` entries, while the query
can return only one. Returning all valid analyses with semantic deduplication
would use existing data more fully. It needs an explicit output/ranking
decision and broader regression checks than the two parsing fixes.

**Update (2026-11-18): done for roots, in lemma mode only.** The lookup now
returns one entry per distinct *root* (2,127 forms belong to more than one), the
old answer first, and lemma mode reads them all; the other modes still read the
first, because `clean_results` re-joins a prefix with one root only. See
[lemma-mode.md](lemma-mode.md#verb-forms-of-several-roots). Several models of
one root, as in `abhavata`, still collapse to the first: the deduplication is by
root.

## Validation and proposed adoption order

Existing suites run via `uv run python`: `tests.test_optimizations`,
`tests.test_compound_inflection`, and `tests.test_analysis_result_contracts`.
**25 tests passed**. Separate read-only probes produced the examples above.
Passing these suites is a baseline check, not evidence that the defects are
covered. No fixes were implemented during this assessment.

For follow-up implementation, define tests first:

1. Add explicit first/second/third-person and all-number cases; add tests for
   both slash alternatives and for forms present in several cells. Correct the
   shared parser, run those tests and the existing suites, and invalidate old
   persisted morphology results via `ANALYSIS_ALGORITHM_VERSION` in
   `utils/analysisCache.py`.
2. Separately test multiple verb models, duplicate base variants, stable output
   order, and public result grouping before changing the one-result policy.
3. Before any data refresh, create a reproducible builder with pinned source
   commits, Huet input date/checksum, explicit conversion and reconciliation,
   and a manifest. Build a separate candidate database. Gate replacement on
   schema/index checks, model-description coverage, paradigm lengths,
   alternative-form lookup, root mappings, per-tense coverage, and reviewed
   row/analysis differences against the current database.
4. Only publish a new database when that comparison demonstrates a useful data
   improvement. Provide an explicit upgrade path for existing installations;
   the current download-if-missing installer is insufficient by itself.

The new Huet extraction fix is worth retaining for step 3. It supplies no
measured coverage gain to justify skipping directly to step 4.
